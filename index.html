Truffle

Local-first, zero-knowledge screenshot knowledge graph

The average person takes 20+ screenshots per day. They accumulate into an unsearchable, unstructured pile of digital clutter. Truffle compiles screenshots into a searchable, interlinked knowledge graph—entirely on your device, encrypted end-to-end, synced without trust.

The Bet

Users will trade cloud convenience for local control when the UX is seamless and the cryptography is invisible

Thesis: privacy-conscious users want their data on-device, but only if sync feels as effortless as iCloud.

Conviction: High. The zero-knowledge sync protocol (ZKS-1) pairs devices with a QR code and 6-digit verification—cryptography that feels like setup, not a CS degree.

Risk if wrong: Users expect iCloud-level sync reliability; any friction in device pairing or sync latency kills adoption.

Hedge: Cloudflare Workers relay provides store-and-forward with 30-day TTL; fallback to manual export/import if sync fails.

"Project Truffle follows a Local-First Architecture with zero-knowledge sync capabilities. The system is designed around the principle that user data never leaves the device in an unencrypted form, and infrastructure operators maintain mathematical inability to decrypt user content." — ARCHITECTURE.md

Solution

  • Stage 1: Ingestion — FileSystem watcher detects new screenshots, priority queue (P0-P2)
  • Stage 2: Preprocessing — Resize to 896px, safety filter (NSFW/medical/banking detection)
  • Stage 3: AI Processing — Gemma 4 multimodal analysis, Tesseract OCR, MiniLM embeddings
  • Stage 4: Knowledge Construction — Schema engine, entity resolution, backlink injection, HNSW vector indexing
  • Storage: SQLite + WAL + sqlite-vec, all encrypted at rest with AES-256-GCM
  • Sync: ZKS-1 protocol with X3DH handshake, AES-256-GCM/ChaCha20, Yjs CRDT deltas

Engineering Proof

Zero-Knowledge Sync Protocol (ZKS-1) vs Cloud Convenience

The decision to build a custom sync protocol instead of using iCloud or Dropbox was fundamental to the product thesis. Cloud services can read your data; ZKS-1 ensures mathematical inability to decrypt. This module implements X3DH handshake, session management, dual-cipher encryption, replay detection, and device trust levels.

pub struct Zks1Protocol {
  identity: IdentityKeyPair,
  device_id: DeviceId,
  config: SyncConfig,
  sessions: RwLock<HashMap<DeviceId, Zks1Session>>,
  signed_prekey: RwLock<SignedPrekey>,
  one_time_prekeys: RwLock<Vec<EphemeralKeyPair>>,
}

impl Zks1Protocol {
  pub fn initiate_session(&self, peer: DeviceId, bundle: PreKeyBundle)
    -> CryptoResult<()> {
    let mut session = Zks1Session::new(peer);
    session.state = SessionState::Handshaking;

    let (initiator, result) = X3dhHandshake::initiate(
      self.identity.clone(), bundle)?;

    let session_keys = SessionKeys::from_x3dh_result(&result)?;
    session.activate(session_keys)?;

    self.sessions.write()?.insert(peer, session);
    Ok(())
  }

  pub fn encrypt_crdt_update(&self, peer: DeviceId,
    crdt_update: Vec<u8>, schema_version: String,
    privacy: PrivacyClassification) -> CryptoResult<SyncMessage> {

    let mut sessions = self.sessions.write()?;
    let session = sessions.get_mut(&peer)
      .ok_or(CryptoError::invalid_state("No active session"))?;

    let keys = session.session_keys.as_ref()
      .ok_or(CryptoError::invalid_state("No session keys"))?;

    let content = CrdtUpdateContent::new(crdt_update,
      schema_version, privacy)?;
    let plaintext = content.to_bytes()?;

    let encrypted = if self.config.use_chacha20 {
      self.encrypt_chacha20(&plaintext, &keys.sync_key)?
    } else {
      self.encrypt_aes256_gcm(&plaintext, &keys.sync_key)?
    };

    let sequence = session.next_sequence();
    let header = SyncMessageHeader::new(self.device_id,
      MessageType::CrdtUpdate, sequence)?;

    let message = SyncMessage::new(header, encrypted, &keys.auth_key);
    session.statistics.record_sent(message.to_bytes()?.len());
    session.touch();
    Ok(message)
  }

  pub fn decrypt_message(&self, message: &SyncMessage)
    -> CryptoResult<CrdtUpdateContent> {
    let peer = message.header.device_id;
    let mut sessions = self.sessions.write()?;
    let session = sessions.get_mut(&peer)
      .ok_or(CryptoError::invalid_state("No session"))?;

    let keys = session.session_keys.as_ref()
      .ok_or(CryptoError::invalid_state("No keys"))?;

    if !message.verify_authenticator(&keys.auth_key) {
      return Err(CryptoError::authentication_failed("HMAC invalid"));
    }
    if !session.validate_sequence(message.header.sequence_number) {
      return Err(CryptoError::replay_attack_detected("Bad sequence"));
    }
    let msg_id = message.message_id();
    if session.is_duplicate(&msg_id) {
      return Err(CryptoError::replay_attack_detected("Duplicate"));
    }
    session.mark_seen(msg_id);

    let plaintext = if self.config.use_chacha20 {
      self.decrypt_chacha20(&message.payload, &keys.sync_key)?
    } else {
      self.decrypt_aes256_gcm(&message.payload, &keys.sync_key)?
    };

    session.statistics.record_received(message.to_bytes()?.len());
    session.touch();
    CrdtUpdateContent::from_bytes(&plaintext)
  }
}
Strategic Decisions

Five decisions that shaped the build

Why build a custom sync protocol (ZKS-1) instead of using iCloud or Dropbox?

iCloud and Dropbox can read your data. ZKS-1 ensures the relay server has mathematical inability to decrypt user content. The protocol uses X3DH for key exchange, AES-256-GCM/ChaCha20 for encryption, and HMAC-SHA256 for authentication. Cloudflare Workers only store encrypted blobs with 30-day TTL. This is the core product differentiator.

High Impact
Why local-first instead of cloud-first?

Screenshots contain sensitive information: receipts, medical records, banking details, private messages. A cloud-first approach would require trusting the infrastructure provider. Local-first keeps raw images on the device, encrypts wiki nodes at rest, and only syncs encrypted ciphertext. The architecture doc explicitly calls this 'mathematical inability to decrypt.'

High Impact
Why defer the AI engine (truffle-ai with Gemma 4)?

The Cargo.toml comments out truffle-ai: 'Deferred — requires Metal/CUDA GPU SDK for llama.cpp.' On-device LLM inference requires GPU acceleration for acceptable performance. The pipeline scaffolding exists and can process artifacts; AI classification currently uses placeholder logic or can be integrated once the GPU dependency is resolved.

High Impact
Why SQLite + sqlite-vec instead of a dedicated vector database?

SQLite is already embedded in the Rust core for structured data. sqlite-vec adds vector search (HNSW index) in the same database file, avoiding a separate process or network dependency. This keeps the deployment footprint minimal and aligns with the local-first philosophy.

Medium Impact
Why Tauri over Electron for the desktop app?

ADR-001 explicitly chose Tauri over Electron for smaller bundle size, lower memory footprint, and better security (Rust backend, OS-native webview). The Tauri v2 bridge provides native OS integration: file system access, notifications, and global shortcuts without shipping a full Chromium runtime.

Medium Impact

Reflection

What worked, what I would change, what I learned

What worked

  • The Rust core library is exceptionally well-structured with clear module boundaries across 11 domains
  • ZKS-1 protocol is a genuine cryptographic implementation—not a wrapper around existing libraries
  • The Tauri desktop app demonstrates mature frontend architecture: Zustand, TanStack Query, React Router, error boundaries
  • Mobile companions implement platform-native patterns correctly: iOS Secure Enclave + BGTaskScheduler, Android Keystore + WorkManager
  • Infrastructure is production-grade: Terraform, K8s, Istio, Helm, full observability stack

What I would change

  • Complete the AI engine integration — llama.cpp scaffolding exists but Gemma 4 is not wired into the pipeline
  • Replace mock data in the desktop app with real Tauri backend integration
  • Implement full X3DH in sync/crypto.rs — current uses simplified HKDF as noted in code comments
  • Add end-to-end sync tests between desktop and mobile
  • Reduce documentation surface — 15+ assessment/progress documents exceed source code in volume

Lessons

  • Local-first architecture is viable for consumer apps when the sync protocol is invisible to users
  • Multi-platform projects benefit enormously from a Rust core library consumed via FFI and Tauri commands
  • Deferring GPU-dependent AI features is correct when the pipeline scaffolding is complete
  • Zero-knowledge is a powerful claim but requires rigorous verification — the verifyZeroAccess endpoint and audit logging prove it to auditors
